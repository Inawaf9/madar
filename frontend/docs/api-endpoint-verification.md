# MADAR Backend Endpoint Verification

Generated from current Spring controller mappings and the frontend audit on 2026-10-28.

## Scope and result

- Discovered **123** controller mappings across 19 controllers. No duplicate HTTP method/path pairs were found.
- Status counts: ADMIN EXCLUDED 20; STATICALLY VERIFIED 92; BLOCKED 1; BACKEND ONLY 4; PARTIALLY INTEGRATED 6.
- No endpoint is marked VERIFIED: no live backend endpoint calls were made. STATICALLY VERIFIED means a frontend caller and static contract path were traced, not a successful runtime response.
- The full endpoint inventory and original caller evidence are in [unused-endpoints-audit.md](./unused-endpoints-audit.md).

## Shared BFF/auth findings

- Business routes are allowlisted in `lib/api/operation-contracts.ts`; private routes require a server-read session and forward the access token as Bearer authorization through `lib/api/backend.server.ts`. Actor IDs are not accepted as query identity.
- Browser mutations require Origin/CSRF validation. The BFF also requires CSRF for payment verification, commute analysis, and credit-consuming comparison GET routes. Query allowlists and duplicate-parameter checks run before forwarding.
- The BFF preserves upstream HTTP status and reviewed backend messages, rejects malformed successful JSON, and maps upstream timeouts/network errors to 504/503. The browser client has a 60-second timeout.
- Auth cookies are encrypted, HttpOnly, Secure in production, SameSite=Lax, and written only in Route Handlers. Refresh is intentionally fail-closed with HTTP 503 before calling Spring because safe durable cross-instance rotation coordination is unavailable. Concurrent refresh safety, token rotation, and stale-cookie races are therefore NOT VERIFIED.
- Backend security configuration disables Spring CSRF (JWT stateless API); browser CSRF here protects the Next.js BFF boundary. Backend authorization is separately enforced by Spring security.

## Findings and fixes

- **Fixed: paid smart recommendations lacked a price/confirmation gate.** Spring reserves `TOP_3_RECOMMENDATIONS` for `POST /api/v1/recommendations/me/smart` (`RecommendationService.java:78-98`). The UI now reads the current price and balance, requires an explicit confirmation, disables duplicate submission, sets mutation retry to zero, and invalidates wallet data after settlement (`features/recommendations/smart-recommendations.tsx:50-82, 100, 241-260`). A static safety test was added. No request was executed.
- **Blocked: refresh rotation cannot be safely enabled in this frontend deployment.** Expected: one successful Spring `POST /api/v1/auth/refresh` per refresh token. Actual: Next returns 503 before Spring is called (`app/api/auth/[operation]/route.ts:46-48`; `lib/auth/refresh-policy.server.ts:4-15`). Spring consumes tokens and revokes the entire family on replay (`RefreshTokenService.java:58-74`), while this stateless frontend has no shared atomic coordinator/idempotent recovery contract. No frontend-only fix can guarantee cross-instance single-flight or prevent stale cookie writes. Required: backend idempotent rotation recovery or an approved durable coordinator with atomic session generation/CAS and stale-response protection. Existing token session expires with the access token; refresh and multi-tab/multi-instance behavior are NOT VERIFIED.
- **Partially integrated: six legacy path-based search endpoints** are still in the BFF allowlist without a page/hook caller; the active search uses the query-based `/api/v1/properties/search` contract. No user-facing failure is established. Recommended follow-up: remove these legacy allowlist operations if no consumer is planned, or add a real product use case and tests.

## Credit and external-provider safety

- Backend credit reservations were found in AI chat, smart recommendations, selected-neighborhood recommendations, commute reports, and one-/multi-home comparisons. The paid frontend paths are explicit actions, use live service-price/balance reads where implemented, and use mutation retry zero; smart recommendations received the missing confirmation gate during this audit.
- Google Places/Routes, Kite, OpenRouter, and Moyasar integrations were identified from backend clients/services. No live calls to these providers, payment creation, paid comparison, commute, or recommendation endpoints were made. The generated matrix notes focused tests where available; other response behavior remains static-only.

## Coverage limitations and backend-only checks

- No real authentication, destructive account operation, payment, credit consumption, Google Routes/Places, Kite, or OpenRouter request was executed.
- Per-endpoint runtime/UI tests are not present for most existing integrations; entries state the actual static or focused test evidence.
- Backend compilation/tests were not run because the Backend tree is read-only for this task; executing Maven would write build artifacts there. Static controller/security inspection found no duplicate HTTP method/path mappings.
